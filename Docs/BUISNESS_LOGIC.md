# Business Logic.md

## UserRole — вычисление роли

Роль **не хранится** в БД как отдельное поле. Вычисляется динамически:

| Условие | Роль |
|---------|------|
| `department_id = 1` (технический отдел, id захардкожен) | `Admin` |
| `departments.head_id = userId` (любой отдел) | `Head` |
| Иначе | `User` |

**Приоритет**: Admin > Head > User.
Если пользователь одновременно в техническом отделе (`id = 1`) и является руководителем
другого отдела — роль `Admin` (техотдел имеет приоритет).

**Admin может**:
- Доступ к `/api/admin` — CRUD пользователей, бан/разбан, сброс пароля
- Редактировать любой отдел через админ-панель
- **Исключение**: технический отдел (`id = 1`) — Admin не может менять его состав
  и руководителя (защита от самоудаления из Admin-роли)

**Забаненный пользователь**:
- Не может войти в систему (блокировка на уровне Auth)
- Все активные RefreshToken отзываются **немедленно** в момент бана
- Не видит чаты, не может читать и писать

## Права в чатах

> Применяется к чатам типа `Chat` (группа). Для `Contact` и `Department` — отдельные правила ниже.

| Действие | Member | Admin | Owner |
|----------|--------|-------|-------|
| Читать сообщения | ✅ | ✅ | ✅ |
| Отправить сообщение | ✅ | ✅ | ✅ |
| Добавить участника | ✅ | ✅ | ✅ |
| Удалить участника | ❌ | ✅ | ✅ |
| Изменить роль участника | ❌ | ❌ | ✅ |
| Редактировать название/аватар | ❌ | ❌ | ✅ |
| Удалить чат | ❌ | ❌ | ✅ |
| Покинуть чат | ✅ | ✅ | ❌ |

> Owner не может покинуть чат — сначала должен передать роль Owner другому участнику.
> Owner не может быть удалён из чата другими участниками.

## Типы чатов

### Contact (личный диалог 1:1)
- Создаётся автоматически при первом обращении к другому пользователю
- Системные сообщения **не создаются**
- Роли (Member/Admin/Owner) не применяются
- Уведомления mute/unmute работают как обычно

### Chat (групповой)
- Создаётся пользователем вручную
- Системные сообщения применяются
- Полная ролевая модель (см. таблицу выше)

### Department (чат отдела)
- Создаётся **автоматически** при создании отдела
- Удаляется при удалении отдела
- Состав участников синхронизируется через **триггеры в БД**:
  - Сотрудник добавлен в отдел → автоматически добавляется в чат
  - Сотрудник удалён из отдела → автоматически удаляется из чата
- Ручное управление участниками через сервисы **не требуется** — управляют триггеры
- Системные сообщения применяются

> ⚠️ Не реализовывать синхронизацию участников Department-чата на уровне сервисов.

### DepartmentHeads (чат руководителей)
- Специальный системный чат для всех руководителей отделов (`Head`)
- Управление аналогично Department-чату
- Системные сообщения применяются

## Сообщения

### Создание
Атомарная операция: одновременно создаётся `Message` + опционально `VoiceMessage` + привязываются `MessageFile`.

### Редактирование
- Только **автор** сообщения
- Без ограничения по времени
- После редактирования: `edited_at` обновляется, `is_edited = true` в DTO

### Удаление
- **Автор** сообщения
- **Admin** или **Owner** чата
- Реализовано как **soft delete** (`is_deleted = true`)
- Содержимое не возвращается клиентам после удаления

### Системные сообщения
- Создаются автоматически сервисом `SystemMessageService`
- Только для `Chat` и `Department` чатов, **не для Contact**
- События: `ChatCreated`, `MemberAdded`, `MemberRemoved`, `MemberLeft`, `RoleChanged`
- Не могут быть отредактированы или удалены пользователями

### Закреплённые сообщения
- Закрепить/открепить может любой участник с правом (уточнить в `AccessControlService`)
- `is_pinned`, `pinned_at`, `pinned_by_user_id` обновляются атомарно
- Изменение состояния транслируется через SignalR (`MessageUpdated`)

| Действие | Условие |
|----------|---------|

## Управление пользователями (Admin)

### Создание пользователя
Валидация (последовательно, первая ошибка — отказ):
1. Username: `^[a-z0-9_]{3,30}$` (латиница, цифры, `_`), нормализуется в lowercase
2. Пароль: минимум 6 символов (расширенная валидация — в `ValidationHelper`)
3. Фамилия: обязательна, не может быть пустой
4. Имя: обязательно, не может быть пустым
5. Username: уникальность в БД
6. DepartmentId: если указан — отдел должен существовать

При создании автоматически создаётся `UserSetting` с `NotificationsEnabled = true`.

### Обновление пользователя (Admin)
- Валидация та же, что при создании (username, surname, name)
- ID в URL должен совпадать с `UserDto.Id` → иначе 400
- Username нормализуется в lowercase

### Обновление профиля (Self)
- Через `PUT /api/users/{id}` — обновляет поля через `user.UpdateProfile(dto)`
- Username меняется отдельно через `PUT /api/users/{id}/username`
- Пароль меняется отдельно через `PUT /api/users/{id}/password`

### Смена username (Self)
- Формат: `^[a-z0-9_]{3,30}$`
- Нормализуется в lowercase
- Проверка уникальности среди других пользователей

### Смена пароля (Self)
- Текущий пароль: BCrypt verify
- Новый пароль: минимум 6 символов
- Ошибка верификации → 401 `Unauthorized`

### Сброс пароля (Admin)
- `POST /api/admin/users/{id}/reset-password`, тело: `{ newPassword }`
- Валидация нового пароля через `ValidationHelper`
- Все активные RefreshToken пользователя **немедленно отзываются**
- Пользователь будет разлогинен на всех устройствах

### Бан/разбан
- `POST /api/admin/users/{id}/toggle-ban` — переключает `is_banned`
- При **бане**: все активные RefreshToken немедленно отзываются
- При **разбане**: токены не восстанавливаются, пользователь должен войти заново

## Общие правила

### Soft Delete
- Сообщения удаляются через `is_deleted = true`
- Физически из БД не удаляются
- Клиент не получает содержимое удалённых сообщений

### Уведомления
- Mention (`@username`) генерирует уведомление типа `mention`
- Если чат замьючен — push не показывается, счётчик непрочитанных всё равно растёт
- Если чат открыт — popup не показывается, только unread-счётчик

### Пагинация
- Максимальный размер страницы: 100 (нормализуется в `BaseService.NormalizePagination`)
- Default pageSize: 15 (основная), 30 (before/after), 50 (around)

### Валидация Username (общее правило)
- Регулярное выражение: `^[a-z0-9_]{3,30}$`
- Нормализация: `Trim()` + `ToLowerInvariant()`
- Применяется при создании и смене username

## Звонки

### Типы звонков

| Тип чата | `isGroupCall` | Поведение |
|----------|---------------|-----------|
| `Contact` (1:1) | `false` | Таймаут 60 сек. `DeclineCall` работает. `CancelCall` завершает для всех |
| `Chat`, `Department`, `DepartmentHeads` | `true` | Таймаута нет. `DeclineCall` игнорируется. Можно войти позже |

### Ограничения

| Правило | Детали |
|---------|--------|
| Максимум участников | 12 одновременно |
| Максимум звонков на чат | 1 активный |
| Системное сообщение | Создаётся при завершении звонка длительностью > 1 сек, только для не-Contact чатов |
| Системное сообщение — исключения | `Cancelled` и `Declined` → сообщение **не создаётся** |

### Причины завершения (`CallEndReason`)

| Значение | Условие |
|---------|---------|
| `Ended` | Все участники покинули или последний вышел |
| `Cancelled` | Инициатор отменил до принятия (Contact) |
| `Declined` | Все адресаты отклонили (Contact) |
| `Timeout` | Никто не принял за 60 сек (Contact) |

### Системное сообщение о звонке

- `SystemEventType.CallEnded`
- Контент: `"Звонок завершён · {M:SS}"` или `"Звонок завершён · {H:MM:SS}"`
- Не создаётся для `Contact` чатов
- Не создаётся при `Cancelled`, `Declined`, длительности ≤ 1 сек
- Рассылается через `ReceiveMessageDto` в чат как обычное системное сообщение
